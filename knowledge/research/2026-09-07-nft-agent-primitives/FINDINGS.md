# Material findings before implementation

The following are bounded observations from the pinned files, with consequences for a future Studio experiment. They are not claims about an unexamined deployed service.

## CIP-26: policy-free structure does not establish trusted authorship

The inspected validator requires the basic fields, then succeeds without checking an attestation when `policy` is absent. Its native-policy branch performs those checks. This may be one layer of a wider trust pipeline; do not reuse the function alone as a complete issuer-authentication verifier. The registry README separately describes trusted-key handling for this case. [Goguen registry entry validation](https://github.com/input-output-hk/offchain-metadata-tools/blob/91eba72d6e5e3b17cd49f625c9546f2c82df5a65/token-metadata-creator/src/Cardano/Metadata/GoguenRegistry.hs#L141), [Cardano Token Registry: current registry and trust rules](https://github.com/cardano-foundation/cardano-token-registry/blob/8a2cd449b86ac6f27a7de34dd0845160a832266b/README.md#L72).

Proposed admission test: a structurally valid policy-free record bearing an untrusted key must remain unauthenticated. A first experiment should inspect explicit imported bytes and a separate trusted-key configuration; publishing or fetching registry data is a later integration choice.

## CIP-45: current implementation transport differs from the specification

The pinned dApp and wallet classes use PeerJS, and the package manifest declares version 1.2.21 with a PeerJS dependency. The Foundation component depends on a version range and asks the user about connecting. This establishes source-level support for a peer API bridge; it does not establish WebTorrent interoperability or every wallet's support. [Cardano peer-connect 1.2.21 manifest](https://github.com/fabianbormann/cardano-peer-connect/blob/03ae3dc15a1524632faff22b343ce9ea0130a67e/package.json#L2), [PeerJS dApp peer transport](https://github.com/fabianbormann/cardano-peer-connect/blob/03ae3dc15a1524632faff22b343ce9ea0130a67e/src/DAppPeerConnect.ts#L1), [PeerJS wallet peer transport](https://github.com/fabianbormann/cardano-peer-connect/blob/03ae3dc15a1524632faff22b343ce9ea0130a67e/src/CardanoPeerConnect.ts#L1), [Connect wallet explicit peer connection UI](https://github.com/cardano-foundation/cardano-connect-with-wallet/blob/47ceba88338f19b576bf72251e8158a7883a5e45/react/src/components/ConnectWalletButton/ConnectWalletButton.tsx#L88), [Connect wallet React dependency manifest](https://github.com/cardano-foundation/cardano-connect-with-wallet/blob/47ceba88338f19b576bf72251e8158a7883a5e45/react/package.json#L8).

The dApp class also permits connection without a `verifyConnection` callback. A Studio wrapper must define consent itself. [PeerJS dApp peer transport](https://github.com/fabianbormann/cardano-peer-connect/blob/03ae3dc15a1524632faff22b343ce9ea0130a67e/src/DAppPeerConnect.ts#L264). Test the exact paired implementations, consent rejection, disconnect, account changes and background suspension before a real signer is involved. Do not claim tracker-independent operation from the CIP name.

## CIP-69: use the normative V3 signature, not the earlier abstract

The CIP abstract discusses a redeemer/context signature; the normative section specifies one context containing the redeemer. The current V3 API forwards one argument, and the current context type includes ScriptInfo with the optional spending datum. [CIP-0069: Plutus Script Type Uniformization](https://github.com/cardano-foundation/CIPs/blob/05ee6bb05982289dbe00c4187b9d54cf90e2e276/CIP-0069/README.md#L54), [Plutus V3 single-argument evaluator API](https://github.com/IntersectMBO/plutus/blob/3ab42a1c886ef77dfb3eb25a72dca833fd7280e4/plutus-ledger-api/src/PlutusLedgerApi/V3.hs#L217), [Plutus V3 ScriptInfo and ScriptContext](https://github.com/IntersectMBO/plutus/blob/3ab42a1c886ef77dfb3eb25a72dca833fd7280e4/plutus-ledger-api/src/PlutusLedgerApi/V3/Contexts.hs#L404).

This supplies useful provenance for the existing capsule architecture. It does not establish that arbitrary compiler handler exports are identical; continue comparing actual bytes and versioned hashes and testing unwanted script purposes.

## CIP-116: JSON interchange is not byte-preserving canonicalization

The source explicitly permits mapping order variation and more than one CBOR encoding for a JSON fixture. It also calls out semantic validation outside JSON Schema. [CIP-0116: Canonical JSON Encoding for Domain Types](https://github.com/cardano-foundation/CIPs/blob/05ee6bb05982289dbe00c4187b9d54cf90e2e276/CIP-0116/README.md#L48). Keep exact original transaction bytes and hashes in every explanation/export.

The README's era table only lists Babbage, while the same pinned directory contains Conway and the linked utility loads both schemas. [CIP-0116: Canonical JSON Encoding for Domain Types](https://github.com/cardano-foundation/CIPs/blob/05ee6bb05982289dbe00c4187b9d54cf90e2e276/CIP-0116/README.md#L32), [CIP-0116 Conway JSON Schema](https://github.com/cardano-foundation/CIPs/blob/05ee6bb05982289dbe00c4187b9d54cf90e2e276/CIP-0116/cardano-conway.json), [CIP-0116 AJV validator utilities](https://github.com/mlabs-haskell/cip-0116-tests/blob/7e423b1648d52501dff859d44387d21065263261/index.js#L8). The utility imports `ajv-formats`, which is absent from its package manifest. These are source observations, not a failed clean-install test. [CIP-0116 tests dependency and license manifest](https://github.com/mlabs-haskell/cip-0116-tests/blob/7e423b1648d52501dff859d44387d21065263261/package.json). Select an explicit era/profile, resolve installation requirements and test semantic boundaries before using this as a dependency.

## CIP-170: digest profile and revocation require resolution

The frontend workflow describes hashing JSON with Blake2b-256. Its helper instead strips a wrapper from the first supplied CBOR label and passes the value bytes to Signify Diger. The Reeve indexer decodes and reserializes a selected CBOR value and uses Blake3-256. [CIP-170 frontend documented workflow](https://github.com/cardano-foundation/cip-170-attestation-frontend/blob/41cef0cd7c820bdf169ceaf55e38f85106f1b2a8/WORKFLOW.md#L140), [CIP-170 frontend digest and metadata construction](https://github.com/cardano-foundation/cip-170-attestation-frontend/blob/41cef0cd7c820bdf169ceaf55e38f85106f1b2a8/lib/keri-utils.ts#L7), [Reeve metadata hashing and identity-event dispatch](https://github.com/cardano-foundation/cf-reeve-indexer/blob/dc7de3172c3cf0d1c0ae3dd17d0604641b4992bd/src/main/java/org/cardanofoundation/reeve/indexer/yaci/ReeveMetadataStorage.java#L107).

The examined indexer's AUTH_END branch has no implementation. Its verifier uses a retrieved KEL event and a stored credential-valid flag when marking a report. These files do not establish the complete historical authority/revocation lifecycle required for a general attestation verifier. [Reeve metadata hashing and identity-event dispatch](https://github.com/cardano-foundation/cf-reeve-indexer/blob/dc7de3172c3cf0d1c0ae3dd17d0604641b4992bd/src/main/java/org/cardanofoundation/reeve/indexer/yaci/ReeveMetadataStorage.java#L176), [Reeve KEL and credential verification service](https://github.com/cardano-foundation/cf-reeve-indexer/blob/dc7de3172c3cf0d1c0ae3dd17d0604641b4992bd/src/main/java/org/cardanofoundation/reeve/indexer/service/KeriService.java#L101).

The review did not execute these implementations or verify Signify's default digest selection. Before making a compatibility claim, pin the algorithm, scope of labels, exact preimage encoding, handling of equivalent CBOR encodings, authorized credential labels, and authority-at-transaction-position semantics. Test revocation and later reauthorization, including out-of-order indexing. KEL availability and fork detection remain dependencies of the chosen identity ecosystem.
